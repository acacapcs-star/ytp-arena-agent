## Day 1 · 7/15 — 從能跑開始

題目零時公布，當天午夜截止。目標只有一個：**先交出能跑的東西佔住分數。**

分工上，一人負責把完整 `strategy.py` 寫出來並整合所有模組，
一人負責調參數與對打測試，一人負責 Dockerfile 與提交。

### 那天最重要的發現：player_id 決定同 tick 勝負

同一份程式碼，跑出來的分數差距大得不合理：

```
我方為 player 1：Final scores: [5, 16]   ← 慘敗
我方為 player 0：Final scores: [16, 5]   ← 完勝
```

**程式碼一個字都沒改。** 追下去才發現規則裡的關鍵：
兩艘船同一個 tick 碰到同一顆寶箱時，**player 0 獲勝**。

這解釋了為什麼後來的版本需要 `PLAYER0_CAPTURE_PRIORITY_MARGIN` 這個參數——
身為 player 1 時，必須算出「我要提前多少才搶得到」，而不是打平就好。

### 第二個發現：複雜策略一度輸給貪心

```
Player 0 = 11, Player 1 = 10
Time used: Player 0 = 0.68s, Player 1 = 1.16s
```

主辦提供的 greedy baseline 只花 0.68 秒，我們的版本花了 1.16 秒——
**演算法更複雜，分數卻沒有更好。**

賽制限制 `game_time_budget` 全場只有 60 秒思考時間、`move_timeout` 每 tick 1 秒，
而 `dt = 0.01s`、`max_ticks = 10000`——換算下來：

```
60 秒 ÷ 10,000 ticks ≈ 每 tick 平均 6 毫秒
```

**6 毫秒要跑完場景判斷、候選篩選、路線規劃與控制修正。** 這一天的教訓直接決定了
後續架構：候選必須先用閉式解預篩，不能對每顆寶箱都跑完整模擬；
`REPLAN_INTERVAL = 20`（每 20 個 tick 才完整重新規劃一次）也是從這裡來的。

超過預算不是扣分，是 `game_time_budget` 失格、直接判輸。

### 當天的迭代節奏

從早上八點題目公布到午夜截止，`strategy.py` 改了三十幾版。
中間反覆出現的問題：

- **8 字型繞圈** — 船接近寶箱時衝過頭，折返又衝過頭
- **目標搖擺** — 錯過目標後修正，但下一顆變得更近，於是換目標，然後重複
- **煞車不足** — 減速了但方向仍朝前，等於沒煞

解法是加入目標鎖定（`lock_counter`，從 50 調到 200）與更早的煞車判斷。
這就是最終版 `MIN_COMMIT_TICKS` 的前身。

### 四場景的分數演進

當天中段的版本：

```
test1（無行星）    7 : 14   輸
test2（有行星）    8 : 11   輸
test3（有行星）   16 : 0    大贏
test4（重疊力場）  5 : 15   輸
```

當晚提交的版本：

```
test1   11 : 10

test3   21 : 0    ← 21 顆寶箱全拿

```

**test3 從 16:0 進步到 21:0——場上 21 顆寶箱一顆不剩。**
但 test2 反而退步了，四個場景的表現始終不均，
這也是後來要做場景辨識、為每張地圖切換整套參數的原因。

當晚提交後結算：**第 1 名。**

## Day 2 · 7/16 — 策略成型

這一天的版本跨度最大：1,329 → 1,779 行，參數 23 → 44。一次加入四樣東西：

- **beam search** 多寶箱路線規劃
- **MPC** 加速度修正
- **對手捕獲模擬**
- **殘局模式**

在此之前 Agent 是「選一顆最近的衝過去」；在此之後它開始規劃
「接下來吃哪幾顆、什麼順序、對手會不會先拿走」。

本地對打（新版 vs 前一天版本，四場景各正反手打一輪，共 8 場）：

```
day2      : 5 勝  89 分
day1_final: 2 勝  77 分
平手      : 1
```

結算掉到第 4。名次下降不代表版本變差——每天都有隊伍在調，
而我們這一版是把架構換掉，參數還沒跟上。

## Day 3 · 7/17–7/18 — 一次失敗的實驗

加入路線記憶（`ROUTE_MEMORY_*`），解決目標反覆搖擺的問題。

同時做了一個叫 **zig zag** 的實驗：讓船在衝刺過程中微幅擺動，
試圖順路擦過更多寶箱、並在對手路線上卡位（構想來自賽車的搶內道）。

實測結果：

| 場景 | 無 zig zag | 有 zig zag |
|---|---|---|
| test1 | 11 | 11 |
| test2 | **14** | 13 |
| test3 | **17** | 14 |
| test4 | 11 | **12** |

**四個場景裡兩個明顯退步，直接回退。**

這跟 `versions/05_refactor` 那一步是同一件事——
不是每個想法都該留下，測不出效果就拿掉。

本地對打（新版 vs 前一天版本）：

```
day3_v2   : 5 勝  86 分
day2_final: 2 勝  80 分
平手      : 1
```

**本地測試贏了，線上結算卻掉到第 5**——這是循環賽的常態：
你的版本有沒有進步，跟你在榜上的位置是兩件事，因為所有隊伍都在同時往前跑。

結算第 5，是五天裡最低的一次。

## Day 4 · 7/19 — 場景辨識

發現四張地圖的障礙物配置與雙方出生點完全固定，可以在開局第一個 tick
用**障礙物數量 + 雙方起始座標**判斷是哪一張，然後切換整套參數。

這是一個明確的取捨：換來針對性表現，代價是失去通用性。
賽制中地圖固定，所以這筆划算——但也因此，這個 Agent
在沒見過的地圖上會退回 generic 模式，表現明顯下降。

結算回到**第 1 名**。

## 最後一天 · 7/19 21:00 截止

最終版 3,022 行、114 個參數。相較前一版增加的主要是：

- 各場景的專屬處理函式（trap 地圖的誘餌與清場、重力圖的特定角落處理）
- 對手阻擋（blocking）與碰撞預測
- 殘局精確模式：剩餘寶箱少於門檻時，beam width 加大、模擬時距拉長
- 分數壓力調節：落後時提高冒險傾向，領先時偏保守

**7/20 正式循環賽結果：35 隊中第 2 名，晉級 Top 15，進入決賽。**

## 五天下來學到的

**一、先能跑，再談好。** Day 1 如果沒有先交出保底版本，後面四天都會是零分。

**二、名次下降不一定是版本變差。** Day 2 換掉整個架構，名次掉了三名，
但那是後面兩天能往上衝的基礎。

**三、測不出效果就拿掉。** zig zag 花了半天做，實測退步就回退，
不因為投入過時間而捨不得。

**四、規則細節可能比演算法更重要。** player_id 決定同 tick 勝負這件事，
影響大過任何一次參數調整。
